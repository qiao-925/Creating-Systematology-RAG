# 结论先行

**是的，你需要分层。**

但更准确地说，你缺的不是单一“任务队列”，而是这几层被混在一起了：

- **收件层**：所有输入先进哪里
- **调度层**：现在到底该推进哪些事
- **项目层**：一个具体事情怎么拆、怎么推进
- **执行层**：此刻手上到底做哪 1-3 个动作

你现在的“乱”，大概率不是执行力差，而是 **不同层级的决策混在一个平面里做**。

我这次按你偏好的 **轻量、先调研后下结论** 来收敛，不给你一套重型 PMO，而是给你一套能长期维持秩序的简化框架。

# 调研后的核心发现

## 1. 各家方法论其实在解决不同问题

- **GTD**
  - 强项是：把承诺从脑中卸载出来，并区分 `Next Action / Project / Area / Goal / Vision / Purpose`
  - 它很适合解决“脑内堆积”“事情没外化”的问题
  - 还强调 **Weekly Review**，也就是系统定期校准

- **PARA**
  - 强项是：把东西放进清晰容器里
  - `Projects / Areas / Resources / Archives`
  - 它适合解决“资料、事项、长期责任混在一起”的问题
  - 但它本身不是执行机制

- **Personal Kanban / Kanban**
  - 强项是：**可视化工作 + 限制同时进行中的工作量 WIP**
  - 它适合解决“什么都在做、什么都没做完”的问题
  - 本质是把执行变成 **拉动式**，有空位才拉新活

- **Covey 重要/紧急**
  - 强项是：提醒你别总被紧急事务牵着走
  - 它适合做上层优先级判断
  - 但它不是完整系统

- **Portfolio Management**
  - 强项是：从更高层做 **选择、排序、控制**
  - 关键点不是“怎么做项目”，而是“哪些项目该活着、哪些该暂停”
  - 这正对应你说的“最宏观调度”

## 2. 真正有效的不是单一框架，而是组合

我的综合判断是：

- **GTD** 负责外化与分层
- **PARA** 负责容器
- **Kanban** 负责执行流
- **Covey / Portfolio Thinking** 负责最上层选择

**没有哪一家单独能解决你的问题。**

# 你为什么会乱

我看你描述，混乱大概来自 4 个根因：

- **[根因1] 承诺没有完全外化**
  - 很多事情还停留在脑中、聊天里、零散笔记里

- **[根因2] 领域、项目、动作混在一起**
  - “长期要维护的事” 和 “可以完成的事” 没分开

- **[根因3] 没有准入机制**
  - 新事情一来就默认变成“正在做”
  - 结果不是队列，而是泛滥

- **[根因4] 同时开工太多**
  - WIP 过高，造成大量半成品和心理负担

一句话：

**你缺的不是任务列表，而是“准入 + 分层 + 限流 + 回顾”四件套。**

# 我建议你的“道法术器”

## 道：总原则

- **[价值优先]** 不是谁更急就先做谁，而是谁更重要、更符合当前阶段
- **[容量优先]** 不是想做多少就开多少，而是系统当前容纳多少
- **[完成优先]** 完成比开工更重要
- **[上层做选择]** 上层不管具体动作，下层不决定人生方向
- **[系统要轻]** 管理系统不能比事情本身还耗神

## 法：五层分层模型

### 1. `Inbox` 收件层
只负责收，不负责做决定。

所有新输入先进入这里：

- 想法
- 待办
- 请求
- 灵感
- 别人丢来的事
- 看到想做的事

**规则**：

- 不允许新东西直接冲进“Doing”
- 先收，后澄清

---

### 2. `Portfolio` 宏观调度层
这是你最缺的那层。

它回答的问题是：

- **现在这个阶段，我到底主推哪几件大事？**
- **哪些先不做？**
- **当前容量允许同时活跃多少项目？**

这层不是任务管理，而是 **选择与资源配置**。

建议只保留：

- `Active`：当前活跃主题/项目
- `Deferred`：明确暂缓
- `Dropped`：明确不做

**核心规则**：

- 活跃项目总数要有上限
- 新项目进入前，先问：**要替换掉谁？**
- 不能所有重要的事都同时活跃

---

### 3. `Areas` 领域层
这是长期责任，不是项目。

比如：

- 健康
- 家庭
- 工作主线
- 财务
- 学习
- 内容产出
- 系统维护

这层回答：

- **我长期要守住哪些盘子？**
- **哪些领域最近失衡了？**

它的作用是防止你只被短期项目牵着跑。

---

### 4. `Projects` 项目层
项目必须是**可完成的结果**，不是长期职责。

好的项目长这样：

- 整理完书签体系
- 搭出一版任务系统模板
- 完成某个脚本重构
- 输出一篇调研总结

不好的项目长这样：

- 学习
- 管理自己
- 内容创作
- 健身

这些是 `Area`，不是 `Project`。

**每个活跃项目最少要有 4 个字段**：

- `Outcome`：完成后是什么状态
- `Done`：怎样算完成
- `Next Action`：下一步是什么
- `Waiting/Blocker`：卡在什么地方

---

### 5. `Execution Queue` 执行层
**只有这一层才是真正的队列。**

建议用最简单的 Personal Kanban：

- `Options`
- `Doing`
- `Waiting/Blocked`
- `Done`

**关键规则**：

- `Doing` 的 WIP 限制为 `2-3`
- `Doing` 满了，不准再拉新任务
- 有阻塞就移到 `Waiting/Blocked`
- 只从活跃项目里拉任务，不从全宇宙任务里拉

这一步非常关键。  
你的系统会不会稳定，往往不取决于你会不会列任务，而取决于你能不能 **拒绝同时开太多**。

# 一条完整的数据流

你可以把整套机制理解成下面这个流：

```text
新输入
-> Inbox
-> 澄清分类
-> (Calendar / Area / Resource / Project Candidate / Someday)
-> Portfolio 准入
-> Active Project
-> Next Action
-> Execution Queue (Options -> Doing -> Done)
```

这里最重要的一点是：

**不是所有输入都会变成活跃任务。**

很多东西会被：

- 延后
- 归档
- 放进资源库
- 变成 someday/maybe
- 直接丢弃

这叫 **准入控制**。

# 最小可落地规则

如果你只想先上一个轻量版本，我建议先用这 7 条规则：

- **[规则1]** 所有新事项先入 `Inbox`
- **[规则2]** 每周只允许 `5-7` 个活跃项目
- **[规则3]** 每个活跃项目必须有且只有一个明确 `Next Action`
- **[规则4]** `Doing` 同时最多 `2-3` 项
- **[规则5]** 新项目进入 `Active` 前，必须暂停或关闭旧项目
- **[规则6]** 长期职责放 `Areas`，不要伪装成项目
- **[规则7]** 每周固定做一次 `Weekly Review`

# 运行节奏

## 每天
10 分钟足够。

- 清一下 `Doing`
- 从 `Options` 里拉 1-3 个动作
- 看有没有阻塞项需要转到 `Waiting`

## 每周
这是系统稳定的关键。

做一次轻量 `Weekly Review`：

- 清空 `Inbox`
- 过一遍所有活跃项目
- 确保每个项目有下一步动作
- 看哪些项目该暂停/删除
- 看哪些领域最近失衡

## 每月
做一次更高层校准。

- 当前阶段主推什么
- 哪些方向不该继续分散精力
- 哪些 `Area` 被忽视了
- 当前活跃项目数是否超载

# 不建议你做的事

- **[不要]** 把所有事情塞进一个超级大列表
- **[不要]** 用几十个优先级标签代替真正的准入控制
- **[不要]** 把“领域”当“项目”
- **[不要]** 让任何新想法直接进入 `Doing`
- **[不要]** 同时开 10 个项目，再靠意志力硬顶
- **[不要]** 一上来就搞很重的项目管理工具流程

- **[事实]** 一个复杂系统应该通过不同的 `viewpoint / view` 去回应不同的关切，而不是强迫一张图同时解决所有问题
