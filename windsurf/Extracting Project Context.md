## 十、Evaluator / Harness 相关启发

从保存的任务里提取到一条重要方法论：

- **生成器和评估器要分离**
  - 做事的 Agent 和判断是否做好的 Agent 不应该混在一起。
- **评估标准要显式化**
  - 不问“好不好”，而是检查是否满足明确标准。
- **评估反馈要可行动**
  - 不只输出 `failed`，而要给出：
    - 问题类型
    - 具体位置
    - 下一步动作
- **Evaluator 本身需要校准**
  - 它不是一次性脚本，而是治理层组件。
- **不要把 evaluator 藏成附属脚本**
  - 它更像 harness 的一级部件。

这对当前项目的映射是：

- CLD 自审、FCM 评估、输出质量判断，都应该逐步走向明确 evaluator / gate 形态。
- 这也支持项目三支柱里的 **评估反馈**。

## 我建议的 MVP 边界

### MVP 名称

### 输入

一个研究问题，例如：

```text

```

### 输出

一个最小结构化结果：

- **CLD 节点**
  - 变量名
  - 变量说明
- **因果边**
  - source
  - target
  - polarity：正向 / 负向
  - rationale：为什么有这条边
- **自审报告**
  - 是否满足 schema
  - 是否存在孤立节点
  - 是否存在无解释边
  - 是否存在明显循环

- **不做 D2D**
